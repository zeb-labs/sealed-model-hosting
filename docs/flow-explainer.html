Secure model hosting - proof of concept

A model the customer can run but never read

A model builder ships its model into a customer's own AWS account. The customer's data never leaves that account, and the customer still cannot read or copy the model's weights. This page shows how that works, first in one picture, then step by step.

The idea in one picture

The key follows the machine's proof of what it booted, not who asks

  1. 1The builder cuts the model into pieces, encrypts each piece, and stores them in an S3 bucket (Amazon's file storage) in the builder's account. The bucket holds unreadable data only.
  2. 2The encrypted release is copied once into the customer's own bucket. It is still unreadable there, and the machine no longer depends on the builder's bucket to start.
  3. 3The builder keeps two master keys in AWS KMS, Amazon's key service. The model key is the only thing that can unlock the model. The lease key is a permit the machine must renew to keep running. The pipeline writes a rule on both: release only to a machine that booted this exact image.
  4. 4At boot, the sealed machine in the customer's account sends KMS a signed proof of what it booted. The proof comes from AWS hardware, so the machine cannot fake it.
  5. 5KMS checks the proof against the rule and returns the model's key, packaged so that only this one boot can open it. Then the machine locks itself so the key cannot be asked for again.
  6. 6The encrypted pieces stream from the customer's bucket to the GPU. Each one is checked against fingerprints inside the image and decrypted in memory. No readable copy is written to disk.
  7. 7The customer's app asks questions over the customer's private network, on HTTPS, with an API key the customer manages.
  8. 8The machine's logs go to the customer's log store (CloudWatch). Fine-tuned add-ons and usage records go to the customer's S3 bucket.
  9. 9The builder may read the usage records, which are counts only, and nothing else on the customer's side.
  10. 10Every minute the machine renews its lease with KMS. If the builder disables the lease key, renewal fails and the machine switches itself off within about two minutes.

The builder keeps

The weights, the build, usage counts, and the ability to switch access off.

The customer keeps

Their data, their logs, their adapters, and full control of the account the machine runs in.

Nobody gets

A shell on the sealed machine. Not the customer, and not the builder.

Words used on this page

Every term, in plain words

Nothing below assumes you know AWS or machine learning. Each term is used the same way in both diagrams.

Keys and proof

AWS KMS
Amazon's key service. It holds master keys that never leave it. You can only ask it to do something with a key, and it checks a written rule (the key policy) before it does.
Model key
A master key in KMS, in the builder's account. It is the only thing that can unwrap the model's data key. Its rule: release only to our exact machine image, and only once per boot.
Data key
The 256-bit key that actually encrypts the model. KMS creates it. It exists in readable form only for a moment: in the build pipeline while encrypting, and in the sealed machine's memory while loading.
Wrapped key
The data key, encrypted by the model key. A 184-byte file stored next to the model, in both buckets. Useless to anyone who cannot get KMS to unwrap it.
Lease and lease key
A lease is a short permit to keep serving. The lease key is a second master key in KMS used only for that: every minute the machine must get KMS to use it. If the builder disables the key, the permit runs out and the machine stops.
Attestation document
A proof of what a machine booted, signed by AWS hardware. It lists the machine's boot fingerprints. KMS reads it and compares it with the key's rule.
Measurement (PCR)
A fingerprint of something that ran during boot, recorded in the machine's TPM. A record can be added to but never rewritten. We use four: the boot file, the Secure Boot state, extra boot settings, and one of our own.
Open state, locked state
Two values of our own fingerprint. Open: the machine has checked its containers and may ask for the model key. Locked: it has asked once, and can never ask again on this boot. The lease key works only in the locked state.

The machine

Sealed image
The disk image the machine boots from. It has no login of any kind, its disk is read-only and verified block by block, and it does one fixed job at boot.
Secure Boot
A firmware check that refuses to start a boot file that is not signed with the builder's key.
NitroTPM
A security component AWS gives each machine. It stores the boot fingerprints and produces the signed proof.
Loader
The first program of ours that runs. It checks the containers, proves the boot to KMS, receives the key once, and locks.
Decrypting proxy
A small program inside the machine. It fetches encrypted pieces of the model, checks and decrypts each one in memory, and hands them to the model server.
Encrypted local disk
A fast disk inside the machine used for the large container and for training. It is encrypted with a random key that exists only in memory, so its contents are unreadable after power-off.
Front gate
A small web server at the machine's only open port (HTTPS, port 443). It asks for an API key and lets the customer's app reach four addresses of the model server and nothing else.
API key
A password for the endpoint. The customer writes their keys in a file in their own bucket; the machine reads it every 30 seconds. No valid key, no answer.
Container firewall
Rules set at boot that stop the model server's container from opening any connection out. It can only fetch the weights from the proxy on the same machine.
Launch tags
Labels the customer's template puts on the machine. Three of them name the customer's bucket, key, and log group, so one image can serve many customers. They are not trusted and open nothing.
Private subnet, endpoint
The machine sits in a network with no route to the internet. It can reach exactly three AWS services through private doors called endpoints: storage, KMS, and logs.

The model

Weights
The numbers that are the model. They are what the builder must protect.
vLLM
The open-source program that serves the model on the GPU. We run it unmodified.
Tensorizer format
A way of laying out the weights in a file so they can be read piece by piece straight into GPU memory.
Chunk
One 8 MiB piece of an encrypted file. Each chunk is encrypted separately and carries its own tamper check.
Tamper check
A 16-byte code on every chunk (AES-256-GCM). If a chunk is changed, swapped, dropped, or cut short, the check fails and the machine refuses it.
Fine-tuning, adapter
Fine-tuning teaches the model from the customer's examples. The result is a small add-on file called an adapter (LoRA). The base weights do not change.

Running and control

AgentCore harness, gateway
AWS AgentCore runs AI agents. A harness is the agent's loop: it thinks and calls tools. A gateway is the fixed list of tools one harness may call.
Release agent (deployer)
The builder's agent. It prepares the build machine and runs the release steps in order by calling fixed tools. It cannot approve a release, write a key rule, or read a secret.
Customer agent
The customer's agent. It creates the customer's one stack, waits for the model, makes an API key, and tests the endpoint. It never sees the key or the model.
Remediation agent
An AI agent called when a step fails, for the builder or the customer. It looks into the failure with read-only tools, applies a fix from a short fixed list, or tells the person exactly what to do. It cannot run commands.
Onboarding
The builder adds one statement to both key rules for one customer's machine role. The measurements are still required. Removing the statement cuts that customer off.
Approval
A record that a human approved one exact build. The keys cannot be tied to an image without it.
Job runner, trainer
The job runner picks up fine-tuning jobs from the customer's bucket and checks the form. The trainer does the training with no network and no credentials.
Usage meter, usage record
The meter counts requests and tokens. Every two minutes it writes a small record of those counts, with a seal, into the customer's bucket.
Seal
A keyed fingerprint (HMAC) on each usage record. The builder can tell if a record was changed; missing numbers in the sequence show if one was removed.
Log shipper
Sends the machine's own log to the customer's log store. It never sends what the trainer prints.
Cut-off
The builder disables the keys. The machine's next lease renewals fail, it stops serving, and it powers off.

Technical detail

    The life cycle

    Where the machine image comes from, how it reaches a customer, and what is created in their account

    Two AWS accounts. The image and the keys are made in the builder's. One stack creates everything the runtime needs in the customer's. The words in small capitals say where each step is on the control page (bash smh.sh ui).

    A - Builder tab: Ship a model

    The builder makes a release

    • The release agent encrypts the model and puts the files in the builder's S3 bucket, one folder per release.
    • The build machine builds the sealed image from the recipe, with the fingerprints of those files inside, and signs it.
    • The image is registered as an AMI in the builder's account. Both keys are tied to that image's measurements.

    B - Customers tab: Onboard a new customer

    The builder onboards a customer

    • The AMI is shared with the customer's AWS account. It is not copied, and it holds no model and no key.
    • The customer's machine role may read that one release folder in the builder's bucket. The files are ciphertext.
    • The keys are never shared. The key policies name the customer's machine role, and still require the image's measurements.
    • An install kit is written: image ID, key ARNs, bucket name, settings.

    C - Customer side tab: Configure this AWS account

    The customer configures their AWS account

    • A small private bucket for the agent's own files.
    • The customer agent and the remediation agent on AgentCore, in the customer's own account.
    • Once per account.

    D - Customer side tab: Bring up the customer's side

    The customer brings it up

    • The customer agent creates ONE stack. It holds everything the runtime needs:
    • a private network with no internet and three private doors (S3, KMS, logs); the customer's own bucket, key and log group; the machine's role; the sealed machine, started from the shared AMI; a load balancer, which is the endpoint.
    • The agent then makes an API key and tests the endpoint.

    E - nothing to press

    Every boot, by itself

    • The machine proves to KMS what it booted, gets the model's key once, locks itself, and streams the encrypted model to the GPU.
    • Logs, adapters and usage records stay in the customer's account. The builder may read usage counts only.

    F - Customer side tab

    Using the model, two ways

    • Way 1, your own application: any program in the customer's network calls the endpoint with the API key. Standard chat API.
    • Way 2, through AgentCore: an agent on AgentCore Runtime inside the customer's network, whose model is the sealed model. It can use tools.
    • Either way the caller only asks questions. The weights never leave the sealed machine.

    G - Customers tab, per customer

    Running, and the end

    • The customer calls the endpoint and fine-tunes with their own data.
    • The builder can pause, resume or remove one customer. A paused customer's machine stops within about four minutes.
    • A new release: Ship a model again; every customer's machine loads it at its next restart.

    Using the sealed model

    Two ways: your own application, or an agent on AWS AgentCore

    Once the customer's side is up, the model can be used in two ways. In both, the call goes to the sealed machine's one HTTPS door with the customer's API key, and the weights never leave the machine.

    Way 1 - direct inference

    Build your own application on it

    • The endpoint speaks the standard chat API (the format OpenAI uses), so existing libraries and tools work unchanged.
    • HTTPS only, one port, and no answer without the customer's API key.
    • Reachable from inside the customer's network only.
    • Fine-tuned adapters are extra model names on the same endpoint.

    Way 2 - through AgentCore

    An agent whose model is the sealed model

    • One command: bash smh.sh agent-up. Then bash smh.sh ask "...", or call it through the AgentCore API.
    • The agent runs on AgentCore Runtime inside the customer's own network. It adds no new way out of that network.
    • It can use tools. The sealed model decides when to call one, the agent runs it and gives the result back.
    • The agent's code is one file. Replace its two demonstration tools (a calculator and a clock) with your own.

    What keeps way 2 safe

    The agent is just another caller

    • It has no key of the model and cannot read the weights. It can only ask questions, like any app.
    • It accepts exactly one certificate, the sealed machine's, by fingerprint. A different one is refused before anything is sent.
    • Its role may read its own code and the customer's API key file, and nothing else.
    • The builder can still pause this customer; the agent then gets no more answers.

    Run on November 28, 2026

    • An agent on AgentCore Runtime, inside the customer's private network, answered real questions with the sealed model. It read the customer's API key itself and accepted only the sealed machine's certificate.
    • Tool use: on releases 0.13.0 and 0.13.1 the sealed model asked for the calculator (17 times 23, answer 391) and for the clock, and used the results.
    • A wrong certificate fingerprint was refused before anything was sent.
    • The builder paused the customer: the sealed machine switched itself off within about five minutes, and the agent got no more answers.
    • On the way: Amazon published a new Linux kernel that night and the release build stopped. The release agent rebuilt and re-signed the GPU driver from one sentence, and the release went through.
    • Not passed: an AgentCore harness using the sealed model with no agent code. It needs a real domain name and a public certificate on the endpoint, and it must sit in its own network: our release check refused a customer network that could reach more than storage, the key service and logs.

    The whole flow on AWS AgentCore

    Three agents run it: one for the builder, one for the customer, one that looks into failures

    Each person runs one command. The command hands the work to an AI agent on AWS AgentCore. An agent here is a harness (the loop that thinks and calls tools) that may call only its own gateway (a fixed list of tools), which runs one function with a narrow AWS role. No agent can run a command of its own, read a key, or read the model.

    Builder, first time: bash smh.sh setup

    • The command creates the fixed pieces that are missing: cost guard, network and bucket, the two keys, the build machine.
    • It sets up the three agents. All use one existing Claude inference profile from a settings file; nothing is created for the model.
    • The release agent checks every piece, starts the build machine and runs one fixed script on it: build tools, Secure Boot keys, a signed NVIDIA driver for the image's kernel, the lease secret. It never replaces a key.
    • It reads back fixed fields, says plainly if the keys are test keys, and stops the machine.

    Builder, each release: bash smh.sh ship

    • The release agent sizes the model and picks a GPU machine.
    • It runs the fixed steps in order: encrypt the model, build and sign the sealed image, register it, run the checks, write the customer's package.
    • It asks for approval. The keys are tied to the image only when a human's approval record names exactly that build; the agent cannot write that record.
    • Then the customer's machine role is given access. The measurements are still required.

    Customer: bash smh.sh up

    • The command writes a small request: which release, and this account's network settings.
    • The customer agent creates the one stack from the builder's package. It chooses only the stack's name and a GPU type from a list.
    • It waits for the sealed machine to prove itself and load the model, then makes an API key. The key is made inside the function and never shown to the agent.
    • It runs a stand-in app inside the network and reports fixed results: health, a call without a key, a real answer, open ports.

    What keeps the agents safe

    • Every input is checked against a list or a pattern. No input carries a command, a policy, or a measured value.
    • Every answer is fixed fields. Log text and console text never come back to an agent that can act.
    • The broad rights needed to create a network or a machine sit in CloudFormation's own role, usable only for stacks of one name, from fixed templates.
    • Automation can change or remove only resources that carry the project's tags.
    • Every decision and tool call is recorded in the account it ran in.

    Run on November 27, 2026

    • Setup: end to end in our account, where every piece already existed. The build machine script was also run on a brand-new machine: ready in 5 minutes, and it then built and signed a sealed image.
    • Release 0.12.0: made by the release agent in 52 minutes, with no failure.
    • Customer side: brought up and tested by the customer agent in 27 minutes. Health 200, no key 401, a real answer 200, only port 443 open.
    • Onboarding: a second customer was registered by account number, given access, sent a kit, configured, and brought up next to the first. Pausing it stopped only that customer.
    • Real failures on the way (a document update, a missing right in a new role, a half-made stack left behind, two test customers in one network, a template mistake of ours). The remediation agent explained each one.

    Not shown, said plainly

    • An empty account in one go, and a second account. Builder and customer agents share our one account; in real life the customer agent lives in the customer's own.
    • The agent does not create the builder's networks, keys, and roles. The setup command does, with the person's own AWS user.
    • The builder's own Secure Boot keys can be supplied; only test keys were run.
    • Fine-tuning is still one command watched by the remediation agent, not driven by the customer agent.

    The complete flow with AgentCore

    From the builder's side, and from the customer's side

    Step by step: what the person does, what runs, which tools the agent calls on AWS AgentCore, and what exists afterwards. An agent can call only the tools named here. Where it says "no agent", a plain command does the step.

    The builder's side

    Two agents work for the builder, in the builder's account: the release agent (harness smh_poc_deployer, eleven tools) and the remediation agent (harness smh_poc_watcher, eight tools that only read).

    1. 1

      Set up, once

      You do

      bash smh.sh setup
      or the button "Set up the builder's side"

      What runs, and what the agent calls

      The command creates the fixed pieces that are missing (network, bucket, two keys, build machine, cost guard) and the three harnesses.
      Release agent: environment → builder_power up → prepare_builder → environment → builder_power down

      What you have after

      A build machine with build tools, Secure Boot keys, a signed GPU driver and the lease secret. The agent reports fixed fields and says if the keys are test keys.

    2. 2

      Ship a model

      You do

      bash smh.sh ship <model>
      One question at the start: approve by itself if every check passes?

      What runs, and what the agent calls

      Release agent: profile_model → choose_machine → start_deployment → machine helper up → start_step lock → machine helper down → machine builder up → start_step build, register, check, package → request_approval

      What you have after

      The encrypted model in the builder's bucket, the sealed image registered as an AMI in the builder's account, six checks, and a summary waiting for approval.

    3. 3

      Approve and tie the keys

      You do

      Nothing, if you agreed at the start and all six checks pass. Otherwise you type the approval.

      What runs, and what the agent calls

      The command, not the agent, writes the approval record. The agent's roles cannot write it.
      Release agent: get_status → pin_keys → start_step check → machine builder down

      What you have after

      Both key policies release only to that image. The image that was live before can no longer get the key.

    4. 4

      Onboard a customer

      You do

      bash smh.sh onboard-customer <name> <their account>
      or the form on the Customers tab

      What runs, and what the agent calls

      No agent. A plain command: it registers the customer, names their machine role on both keys, shares the release (the image, and read on one folder of encrypted files) and writes the install kit.

      What you have after

      A folder kits/<name>/ to send to the customer. It holds no secret.

    5. 5

      Run the business

      You do

      customers, customer pause | resume | remove <name>, usage, models

      What runs, and what the agent calls

      No agent. Each command changes the registry and both key policies for that one customer.

      What you have after

      A paused customer's machine stops within about four minutes. The others are not affected.

    6. !

      When any step fails

      You do

      Read the finding. Do the numbered steps if there are any, then run the same command again.

      What runs, and what the agent calls

      Remediation agent (read only): stack_failures, step_log, key_access, my_permissions, account_limits, model_info → decide.
      On the builder's side it may choose: run again, wait and run again, give a customer access.

      What you have after

      The step runs again by itself, or you get the cause and exact steps. Every decision is recorded in your bucket.

    The release agent can never: approve a release, write a key rule, read a log, read the model, or run a command of its own.

    The customer's side

    Two agents work for the customer, in the customer's own account: the customer agent (harness smh_poc_customer, six tools) and the customer's own copy of the remediation agent. A third, optional one is the customer's own: an agent on AgentCore Runtime that uses the sealed model (step 6).

    1. 1

      Receive the kit

      You do

      Get the code. Copy the kit's smh.env into it and fill in three lines: your AWS profile, your owner tag, a Claude inference profile your account may use.

      What runs, and what the agent calls

      No agent.

      What you have after

      Settings for your own AWS account, with your stack's name as the builder registered it.

    2. 2

      Configure your AWS account, once

      You do

      bash smh.sh customer-setup <kit folder>
      or the button "Configure this AWS account"

      What runs, and what the agent calls

      No agent yet. The command creates a small bucket for the agent's files, stores the builder's install package, and creates two harnesses in your account: the customer agent and the remediation agent.

      What you have after

      Two agents on AgentCore in your own account. Nothing of the model is in your account yet.

    3. 3

      Bring up

      You do

      bash smh.sh up
      or the button "Bring up the customer's side"

      What runs, and what the agent calls

      The command writes a small request (which release, your network settings).
      Customer agent: status → install g5.xlarge (another GPU type if there is no capacity) → status until the model is ready → make_api_key → test_endpoint → status → remove_test_app

      What you have after

      One stack: a private network, your bucket, your key, your log group, the machine's role, the sealed machine started from the shared image, and the endpoint. An API key on your own machine. A passed test: health 200, no key 401, a real answer 200, only port 443 open.

    4. 4

      Every boot

      You do

      Nothing.

      What runs, and what the agent calls

      No agent. The machine proves to the builder's key service what it booted, gets the model's key once, locks itself, and loads the model.

      What you have after

      The model answers. You cannot read it; the builder cannot read your data.

    5. 5

      Use it, way 1: your own application

      You do

      Call the endpoint from your app with the API key. It speaks the standard chat API. bash smh.sh finetune <file.jsonl> teaches it from your data.

      What runs, and what the agent calls

      No agent. Fine-tuning is a plain command, watched by the remediation agent.

      What you have after

      Answers, and adapters under your own key. Logs and usage records stay in your account; the builder may read usage counts only.

    6. 6

      Use it, way 2: through AgentCore

      You do

      bash smh.sh agent-up, once. Then bash smh.sh ask "...", or call the agent through the AgentCore API from your own programs.

      What runs, and what the agent calls

      The command reads the sealed machine's certificate fingerprint from its log, makes the agent's role, and creates an agent on AgentCore Runtime inside your network. For each question the agent calls the sealed endpoint (/v1/chat/completions); when the model asks for a tool, the agent runs it and calls again.

      What you have after

      An agent on AgentCore whose model is the sealed model, with tool use. It has no key of the model; it accepts only the sealed machine's certificate.

    7. !

      When any step fails

      You do

      Read the finding. Do the numbered steps if there are any, then run the same command again.

      What runs, and what the agent calls

      Remediation agent (read only): stack_failures, machine_log, my_permissions, account_limits → decide.
      On your side it may choose: run again, wait and run again, another GPU type, clear its own half-made stack, restart the machine, a new API key.

      What you have after

      The step runs again by itself, or you get the cause and exact steps, for example the words to send the builder when you have no access yet.

    The customer agent can never: see the API key, see the model, choose the image or the keys (they come from the builder's install package), or touch a stack with another name than this customer's.

    In the proof of concept both sides ran in one AWS account. The customer's steps were run there end to end; the parts that only matter across two accounts are written and were not run.

    Original and ours

    What we kept from the AWS sample, what we changed, what we added

    The starting point is the AWS sample sample-guarded-user-controlled-attested-runtime-deployment (commit b82acf7). The full item-by-item list is in docs/changes-vs-original.md in the repository.

    Kept, unchanged

    • The core idea: KMS releases the key only to an EC2 instance whose NitroTPM attestation document shows it booted one exact sealed image.
    • A sealed Amazon Linux 2023 image built with KIWI: a signed boot file and a read-only, verified disk.
    • vLLM as the model server.

    Changed: gaps closed

    • No way in. The sample image installs a remote-login agent and runs a web terminal with no login next to the model. Ours has no login of any kind and one HTTPS port that needs an API key.
    • No remote command channel into the machine or the model's container.
    • Four measurements pinned in the key policy instead of two, with Secure Boot and our own keys.
    • One key release per boot, then the machine locks itself.
    • Containers and model files verified before any key is requested.
    • Tamper-checked encryption in chunks; the model streams to the GPU, so its size is not capped by machine memory.
    • Logs stay with the customer; the builder sees usage counts only.
    • Measurements written to the key policy by the pipeline, not by hand.

    Added

    • Fine-tuning on the customer's private data: a form and data, never code.
    • Revocation: a lease renewed every minute, per customer.
    • One image for many customers.
    • Two commands instead of eleven manual steps: one for the builder, one for the customer.
    • Any open model by name, or the builder's own weights from a folder, a network share, or S3.
    • Three agents on AWS AgentCore: a release agent, a customer agent, and a remediation agent (section above).
    • One command for the builder's first-time setup.
    • A suite of 33 tests, eight of them attacks, and a cost guard.

    The remediation agent: it watches every run, for builder and customer

    Each side runs one command. When any step of it fails, an AI agent is called with the step's output. It is the same agent on both sides; only the list of fixes it may choose differs. It runs on AWS AgentCore as its own harness, apart from the agents that act.

    • It investigates with tools that can only read: why a stack failed, what the sealed machine logged, what the keys are tied to, what the person's AWS user is allowed to do, account limits, and facts about the model.
    • It fixes what is safe. It picks one fix from a short fixed list (wait and retry, try another machine type, remove its own half-made stack, restart the machine, make a new API key, give a customer access) and the step runs again.
    • It tells the person exactly what to do for everything else, in numbered steps, and continues from the same step once that is done. Examples: a missing permission (with the exact actions to request), an account limit, a model that cannot be released.
    • What keeps it safe: it cannot run commands, it never proposes switching a protection off, a fix that its side may not do becomes a request to a person, and every case is saved for review.
    • Seen in real runs: a customer with no access to the keys, a gated model on the builder's side, no free GPU capacity (it waited and retried by itself), a fine-tune job over the builder's limits, and a real AWS "access denied" for a user who lacked the right to create the stack (it named the exact permissions to request). On November 27: a CloudFormation update that could not go through, a missing right in a new role, and a half-made stack left behind.

    Shown by running it

    • The key goes only to the exact image: seven attack boots ended with no key or no model, and our own admin user was refused the key.
    • No way in: no login prompt, one open port (HTTPS), and no answer without the customer's API key. Given a role and network path for AWS remote management, the machine still never registered.
    • The machine loaded the model from the customer's own bucket. The model server's container could open no outbound connection, and serving and fine-tuning still worked.
    • Asked to hibernate (save memory to disk) while holding the key, the machine wrote no memory image.
    • One-click setup: one stack brought up a second, separate customer on the same image. Its logs, usage records, and adapters went to its own bucket and log group. One command fine-tuned and served an adapter. After a restart the same endpoint name answered.
    • The sealed model used through AWS AgentCore: an agent on AgentCore Runtime inside the customer's network answered with the sealed model, used tools, refused a wrong certificate, and went quiet when the builder paused the customer.
    • Many customers, each managed alone: two customers served side by side on one image. One was paused; its machine logged that the builder withdrew the lease and switched itself off about five minutes later, while the other kept answering. A customer is onboarded with a name and their AWS account number.
    • A remediation agent watched those runs on both sides and handled more than ten real failures: it explained them to a person, and fixed one by itself.
    • Two commands do the whole job: one for the builder (release, approval, keys, customer access; about an hour, one question at the start) and one for the customer (network, machine, API key, test call; about 25 minutes). Both were run on real machines.
    • Plain weights never touch the system disk: after serving and training it was byte-for-byte the released image.
    • Network logs show traffic only to storage, KMS, and the customer's log.
    • Fine-tuning takes a form and data, never code; bad forms are refused.
    • The builder's role can read usage counts and nothing else on the customer's side.

    Not shown, said plainly

    • One AWS account. Builder and customers are separate sets of resources in it. The real wall needs a second account.
    • The one-click template was run inside an existing network, because the test account is at its limit of five networks. Its normal path, creating its own network, was not run. The launch link was produced, not clicked.
    • Host memory is not flat: it grows by about 3 parts in 10 of the model's size, and loading needs about twice the model's size in GPU memory.
    • The build is not reproducible yet, so a customer cannot rebuild and compare.
    • What many adapters reveal about the base weights is not measured.
    • A person does not read each release before it is approved. The builder agrees once at the start, and the release is approved only when its six automatic checks pass. A stricter mode, where a person types the approval after reading the summary, exists; it has not been shown with a person. Approver credentials must be separate from all automation.
    • Secure Boot uses test keys. Two small models on one GPU have gone through end to end: an open model by name, and the builder's own weights from a folder. Large models and other architectures are untested.
    • The endpoint's certificate is made fresh at each boot and is self-signed; the app pins its fingerprint from the log. The endpoint's name stays the same across restarts, but the certificate is not signed by a public authority.
    • A bug in the model server could still be used from inside its container; the firewall closes only the network way out.
